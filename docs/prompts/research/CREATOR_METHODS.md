# Creator methods: attributable evidence and limits

Research cutoff: **2026-10-09**. This report records published practices of **Boris Cherny, creator of Claude Code**, and **Peter Steinberger, creator of OpenClaw**. Their methods are examples under stated circumstances, not a common recipe or proof that a prompting technique works for every model. No account settings, model configuration, installed software, or event application code were changed for this research.

## What the evidence supports

Both make progress easier to judge by giving agents relevant code and documentation, executable checks, and feedback from using the product. They differ on planning interfaces and coordination. Cherny's January posts favor reviewed plans and specialist agents. Steinberger's late-2025 and February-2026 accounts favor conversation, visible terminal sessions, and product iteration. Later evidence adds prompt ablation from Cherny and an explicit call for agent-prompting loops from Steinberger. **None of the creator sources reviewed endorses a named Graph of Thoughts or generic “graph prompting” algorithm.** This is a bounded search finding, not proof that neither has ever discussed one. [Cherny, January 2](https://x.com/bcherny/status/2007179832300581177), [Steinberger, December 28](https://steipete.me/posts/2025/shipping-at-inference-speed), [Cherny, July interview](https://www.ycombinator.com/library/UN-boris-cherny-building-claude-code), [Steinberger, June 7](https://x.com/steipete/status/2063697162748260627).

## Cherny: supported practices

- **Reviewed planning.** In B1 he describes discussing a plan before implementing a PR. B2 reports teammates reviewing a plan with a second session and returning to planning when execution diverges. This supports explicit uncertainty resolution and replanning; it does not establish that every small edit needs a formal plan. [Personal planning post](https://x.com/bcherny/status/2007179845336527000), [team planning post](https://x.com/bcherny/status/2017742745365057733).
- **Scoped parallel work.** B1 describes several terminal and web sessions. B2 distinguishes his multiple Git checkouts from teammates' worktree preference. A worktree is workspace isolation; it does not itself discover task prerequisites or prevent semantic integration errors. [Parallel-work post](https://x.com/bcherny/status/2017742743125299476).
- **Reusable checks and simplification.** B1 identifies a code-simplifier, an end-to-end verify-app agent, and formatting hooks. He gives verification special emphasis and describes browser testing followed by iteration on behavior and UX. His stated quality multiplier is an anecdotal claim, not a controlled estimate. [Specialist-agent post](https://x.com/bcherny/status/2007179850139000872), [verification post](https://x.com/bcherny/status/2007179861115511237).
- **Curated context, followed by removal experiments.** The January posts describe shared repository instructions and corrections. B3 describes removing prompt text and restoring it piece by piece to measure contribution; add guidance only when observed failures repeatedly justify it. He also says evaluations can saturate. This is evidence for empirical maintenance, not indefinite accumulation of rules. [January context post](https://x.com/bcherny/status/2017742747067945390), [July interview, 3:21–10:30](https://www.youtube.com/watch?v=qyPCVqFUyDo&t=201s).
- **Sequence, parallelism, and verification stages.** B3 describes dynamic workflows that run agents in stages, with later agents checking or summarizing earlier results. He characterizes the composition as an algebra for agents. This supports orchestration as a real product concept, but does not prescribe a particular graph-prompt schema. These feature claims are reported interview content; their actual API and availability require separately verified current documentation. [July interview, 24:42 onward](https://www.youtube.com/watch?v=qyPCVqFUyDo&t=1482s).

B3's instruction to delete old instructions is strong and broad. Its useful methodological content is **ablation and remeasurement**. Applying it to ScopeWatch should mean testing optional guidance while preserving human requirements, security boundaries, evidence contracts, and repository obligations. That last sentence is a project-specific inference, not a Cherny quotation.

## Steinberger: supported practices

- **Planning without a required UI mode.** P2 describes discussing the problem, exploring code, and sometimes saving a plan before building. P3, around 1:33:43–1:35:46 in the transcript, repeats conversation-first planning and directing the agent to inspect code before asking questions that code can answer. Opposition to mandatory plan mode is not opposition to thinking or planning. [P2](https://steipete.me/posts/2025/shipping-at-inference-speed), [P3](https://lexfridman.com/peter-steinberger-transcript/).
- **Agent-readable architecture and context.** P2 discusses dependency/framework selection, client/server boundaries, data flow, subsystem documentation, a documentation index, and pointers to known solutions in neighboring projects. P3, around 1:06–1:13, explains the agent's incomplete view of a codebase and why useful pointers and predictable names help. This is context engineering and system design; neither source calls it a formal context graph. [P2](https://steipete.me/posts/2025/shipping-at-inference-speed), [P3](https://lexfridman.com/peter-steinberger-transcript/).
- **Verification that agents can execute.** P2 begins with a CLI that the agent can run and inspect. P3 describes local tests, release stabilization, asking about missing corner-case tests, and maintaining documentation in the implementation session. It retains a role for remote CI and a goal that main remain shippable. [P2](https://steipete.me/posts/2025/shipping-at-inference-speed), [P3, around 1:13:57–1:14:57 and 1:38](https://lexfridman.com/peter-steinberger-transcript/).
- **Human product feedback.** P1/P2 describe inspecting the live product, screenshots for UI problems, and shaping features through use. P3, around 1:20–1:21, rejects assuming a complete product idea can be handed to an orchestrator without losing human judgment. These sources support a working feedback loop; they do not supply a universal production UI checklist. [P1](https://steipete.me/posts/just-talk-to-it), [P3](https://lexfridman.com/peter-steinberger-transcript/).
- **Parallelism with limited ceremony.** P2 describes several projects, queued related work, and rare worktree use. It explicitly notes that his mostly solo approach would not fit a larger team. P3 repeats his preference for visible terminal sessions and simplicity. Do not turn his personal shared-checkout approach into an instruction for concurrent agents to modify the same files. [P2](https://steipete.me/posts/2025/shipping-at-inference-speed), [P3](https://lexfridman.com/peter-steinberger-transcript/).
- **Refactor after learning.** P3, around 1:36–1:38, says he asks what could be improved after implementation, when the agent has learned the constraints and failure points. This makes a simplification review concrete: assess the implementation and its behavior, rather than repeating a “production engineer” persona. [P3](https://lexfridman.com/peter-steinberger-transcript/).
- **Later emphasis on loops.** P4 calls for loops that prompt agents. The post provides no termination rule, evaluation metric, tool design, dependency graph, or resource budget. It updates the evidence beyond the earlier conversation-first articles; attributing a specific implementation to him would exceed it. [P4](https://x.com/steipete/status/2063697162748260627).

The often-repeated “doesn't read code” interpretation is too broad. In P3, around 1:02:46–1:03:39, he distinguishes routine code from database changes he reviews. Around 1:15:55, he says he inspects incoming PR code because it may contain malicious changes. Short prompts also presuppose code inspection, domain knowledge, documentation, and an experienced operator; they are not evidence that requirements can be omitted. [P3](https://lexfridman.com/peter-steinberger-transcript/).

## Keep the graph meanings separate

These are working distinctions for a project prompt, not creator-defined terminology.

| Meaning | What it represents | What creator evidence actually says |
|---|---|---|
| Task dependency DAG | Work items and prerequisite edges; identifies what is ready and what must wait. | Cherny discusses staged orchestration. No reviewed creator source mandates an explicit DAG in every prompt. |
| Code/dependency graph | Modules, imports, libraries, schemas, callers, and data flows in the system being changed. | Steinberger discusses architecture, dependencies, and targeted code inspection. That is evidence to inspect relationships, not to claim he uses a particular graph tool. |
| Native task graph | The harness's tracked tasks, owners, statuses, and blockers. | D1 documents shared tasks and automatic dependency unblocking. This is a tool capability, not a reasoning-method endorsement. |
| Context/evidence graph | Links from decisions to source contracts, relevant files, observations, and checks. | Both discuss relevant context and feedback. Calling a project's evidence map a graph is our implementation choice. Neither reviewed creator source prescribes this formal graph. |
| Graph of Thoughts | A separately named reasoning method; it is not synonymous with any dependency list or multi-agent workflow. | No endorsement found in the reviewed primary creator sources. Do not attach either creator's name to it. |

Current official agent-teams documentation recommends independent work and warns that coordination costs rise for sequential tasks, same-file edits, and many dependencies. It also distinguishes subagents from teammates with independent context windows. Consequently, **use a task graph to expose required ordering, then parallelize only what is actually independent** is a reasonable project inference; “more agents always improves quality” is unsupported. [D1](https://code.claude.com/docs/en/agent-teams#when-to-use-agent-teams).

## Consequences for a ScopeWatch prompt

These are synthesis choices, not quotes or universal creator prescriptions:

1. Read the repository's authoritative contracts and identify uncertainty before implementation. Express necessary prerequisites and evidence gates in a small task DAG; retain a critical path and limited optional work.
2. Give each task a scoped deliverable, relevant context, acceptance evidence, and owner. A graph node is complete when its behavior and evidence meet the contract, not when an agent announces completion.
3. Delegate independent research, reviews, or modules with distinct file ownership. Integrate through one reviewer; rerun meaningful checks when integration changes behavior.
4. Close the loop with executable checks, current-source readback, fresh native evidence, and a visible UI walkthrough. Screenshots help evaluate layout; they cannot prove backend authorization or analytical correctness.
5. Replan when a prerequisite fails. After implementation, inspect simplification opportunities and missed cases using the accumulated context. Keep unresolved assumptions explicit.
6. Reassess optional prompt instructions against observed failures. Preserve human and repository requirements. Avoid creating a large persona catalog, mandatory orchestration stack, or vendor-setting change because a creator used it once.

## Search limitations and rejected shortcuts

Firecrawl search and selective scrape supplied primary author pages, indexed author posts, native interview transcripts, and official tool documentation. Two dedicated developer-index searches for task dependencies returned mainly third-party material; those results were **not** used as official contracts. D1 was fetched directly after that limitation was observed.

`agent-reach doctor --json` could not run because the executable is absent. No installation or account setup was attempted. Its documented YouTube route, available `yt-dlp`, verified B3's date. Captions for the June 25 Steinberger talk, [uploaded July 2 by organizer Greg Kamradt](https://www.youtube.com/watch?v=82YaJw-_t10), returned HTTP 429; no claims from that talk are included. A Threads mirror fetch was unsupported. The Firecrawl X extractor rewrites some `CLAUDE.md` text into a documentation URL; repository-instruction descriptions are paraphrased, and no such transformed text is presented as an exact quotation.

Searches found many secondary summaries, viral tips, and interview takeaways. They were useful for discovering original sources but were not promoted into first-person claims. Search coverage is not exhaustive, and “current” here means the latest **verified published evidence found**, with every practice retaining its publication date. Historical model rankings, context sizes, permission flags, pricing, and installation choices are not recommendations or changes authorized by this report.
