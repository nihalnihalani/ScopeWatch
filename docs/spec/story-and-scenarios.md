# ScopeWatch: the strongest honest story and adversarial scenario matrix

Prepared 9 October 2026 IST. Product and planning analysis only. No project implementation, source finding, account test, exploit, hosted session, policy action or benchmark was performed. This document independently challenges the current [ScopeWatch decision](FINAL_IDEA.md), [independent verdict](../research/debate-archive/07_devils_verdict.md) and earlier [CrossedLine decision](../research/debate-archive/06_FINAL_DECISION.md). It uses their existing primary-source audit; it adds no fresh web-retrieval claim. Akash is excluded.

## 1. One strongest story

**ScopeWatch helps an operator contain a workload that exceeds its approved integration-use allowance, while preserving legitimate work using the same shared credential.**

The person is the operator responsible for several AI workflows, not an abstract SOC and not a developer looking for any vulnerability. Their practical dilemma is: “Something is requesting more access than I approved. If I revoke the shared integration credential, I stop the legitimate job too. Can I identify the right workload, make a reviewable decision, and stop its subsequent operations?”

Use a support-triage workload and a separately installed, preapproved bulk-review workload in one owned repository integration with synthetic content. The support workload has a small rolling approval-event allowance. The bulk workload has a much larger operator-approved allowance for legitimate maintenance work. The operator declares both before running the case. The support workload then makes the selected operation in several real, short Guild sessions. Each operation is locally allowed. Its cumulative approvals exceed its allowance. The bulk workflow may have a higher raw count but remains compliant with its own policy.

ClickHouse selects the actual breached workload and returns its contributing sessions. A real Guild investigator reads the operator-owned manifest and bounded native/query evidence, creates an actionable repository incident, and proposes a precise containment scope. The operator approves that concrete scope. Guild denies a subsequent relevant operation for the target workload. The bulk workload, using the same integration credential, actually completes a fresh legitimate operation after the change.

**The payoff is the conjunction of two observed outcomes: the target is denied, and useful approved work still succeeds.** Merely displaying an alert, opening an issue, or displaying ALLOW for the control is insufficient.

The support run represents a **controlled compromised-agent scenario**, disclosed in the demo. It is deliberately driven beyond the allowance in an owned lab. The minimum system establishes a policy violation; it does not establish how the agent became compromised, whether it is malicious, what data it received, or whether information left the system. “Compromised” describes the scenario setup, not the detector's conclusion.

Suggested opening:

> “This shared credential powers two approved workflows. One workload exceeded the access approvals its owner allowed across sessions. We contained that workload, then verified that the approved bulk job still worked.”

Suggested conclusion:

> “The evidence identifies the workload and policy that changed. This denied repeat and this fresh successful control show the scope of our containment.”

Avoid “documents stolen,” “caught prompt injection,” “prevented exfiltration,” “stopped the first bad call,” and “the AI knows the task was off scope” unless separate trusted evidence actually supports the specific claim.

### Where the “just rate-limit” objection is correct

The minimum detector is a counter against an operator-declared rolling budget. A conventional token bucket, gateway circuit breaker or relational database can implement parts of it. Counting several sessions does not invent a new security category. WorkOS already recommends scoped budgets and NVIDIA already describes monitoring and containment; the prior [verdict's novelty discussion](../research/debate-archive/07_devils_verdict.md) records these first-party sources.

Do not win this argument by pretending an LLM is necessary to count, inventing a destination field, or calling a quota event theft. The defensible product emphasis is **accountable selective containment with verified business continuity**, supported by cross-session attribution, explicit bulk exceptions, a reviewable incident and real residual-access checks. ClickHouse makes the aggregate and contributing evidence inspectable; Guild makes the hosted work and enforcement inspectable. The database's high-scale performance remains a separate measured demonstration, not proof that only ClickHouse could solve the small case.

This is an established control assembled into a focused working product. Its strongest Pi pitch is its usefulness and the clarity of the preserved-work outcome, not novelty of rate limiting. If judges chiefly reward an unexpected new exploit or research idea, the minimum may be a weak Pi entry. That uncertainty cannot be fixed with narrative alone.

### The useful investigator, and its limit

The investigator should answer: which policy version applied, which completed sessions contributed, whether a trusted bulk exception applies, what evidence is missing, and what exact scope the operator should review. It should write a usable incident with citations, rather than summarize arbitrary telemetry or assign an invented severity.

A template can also create an issue from a simple counter. That remains a legitimate devil's argument. Guild's contribution is real hosted source/context reads, mediated credentials, bounded permissions, the incident action and enforcement verification. Do not claim semantic reasoning that the real run does not display. One investigator is enough; swarms, a patch factory and autonomous policy editing add little to this story.

## 4. Fixed policy and evidence contract

1. **The operator owns policy.** Record the installed-workload identity and workspace, connected credential where available, selected operation family, rolling window, allowed count, explicit approved-bulk allowance, and policy version before the run. A local workload label is display metadata until authenticated platform/controller binding establishes who it represents.
2. **Count unique ALLOW decisions.** Native decision-event IDs are the deduplication keys. A replayed row is not another allowed attempt. A genuine retry with a new native decision is another approval event, even if the downstream operation fails. DENY/ERROR are separate context, not silently added to the ALLOW count.
3. **Declare time semantics.** Use an established native event timestamp for event-time windows, or explicitly label collector-observation windows. Late events may revise historical counts. Missing timestamps do not become zero or invented event time. Show persistence/ingestion delay separately from SQL latency.
4. **Bind scope outside the model.** The controller's launch record and authenticated platform metadata establish workload identity. An agent-written actor, purpose, tenant, credential, task or recipient string cannot authorize itself or steer the policy target.
5. **Approval reviews the actual action.** The operator sees case evidence and exact actor/credential/operation/resource scope before approving. Changed evidence or scope requires renewed review. The investigator has no manifest-write or policy-edit authority.
6. **Verify actual effect.** Save native policy details and the first observed subsequent denial. Save a genuinely fresh successful control result after the policy change. Neither a policy-API success response alone nor a local stopped-process flag proves enforcement.
7. **Uncertainty remains visible.** Unknown actor, missing credential binding, partial collection and unsupported resource context produce incomplete-evidence states. They do not prove safety, and should not trigger a blind shared-credential shutdown through the LLM.

### The completed live core should actually prove these cases

Run one normal workload case, one genuine approved bulk workflow, one multi-session breach, one duplicated native ID, one ALLOW followed by failure, and one containment sequence that includes new-session/repeated-call denial plus fresh successful bulk control. Together these directly cover rows 1, 2, 3, 5, 7, 12, 14, 27 and 30 without nine separate applications.

## 6. Scope priority and cut order

**P0 — preserve the story:** one owned integration, two authenticated installed workload identities sharing a credential, one versioned manifest, one selected ALLOW event unit, several completed sessions, one query selecting the actual target, one genuine hosted investigator/issue, one reviewed native DENY, target repeat denial and successful control after that change.

**P1 — preserve correctness:** native-ID deduplication, explicit window clock, missing-evidence visibility, ALLOW/failure semantics, trusted actor binding, exact scope/approval receipt and the evidence links. These make the result believable. Show recorded verification when a live stage run would add risk, labeling it honestly.

**P2 — earn the analytics lane:** a diverse labeled replay/load corpus, varying identities, operation/decision/time/policy cohorts, duplicates and late arrivals; actual stored/queried row counts, query identifiers and bounded p50/p95 measurement. Keep authentic native case rows separate. Start small after the complete loop; a million rows is optional, not a verified prize floor.

**P3 — optional stronger security claims:** trusted resource/recipient/outcome receipts, actual prompt influence, group budgets, recovery automation and richer investigation. Each adds a proof obligation. None is necessary to keep the same minimum product useful.

Cut in this order: automated recovery → actual prompt-influence demonstration → recipient/resource extensions → success/byte analytics → extra operations/integrations → fancy observability UI → large replay row target. Never cut the fresh successful control. If genuine native scoped denial fails, keep the same monitoring/review product but remove the completed-containment claim; that is a weaker entry, not a successful fallback with the same evidence.

## 8. Three strong devil's arguments, with honest answers

### Devil 1: “This is a rate limiter with a database and an issue-writing LLM”

**The criticism is substantially true for the minimum.** Counters, budgets and circuit breakers are old. A tiny trace needs neither a high-performance analytics service nor an LLM to detect the crossing. Calling the same counter “scope intelligence” does not add value.

The best answer is a completed operational decision with trustworthy attribution and collateral checks: the operator sees the cumulative native evidence, excludes preapproved bulk work, reviews a precise target, applies real native control and sees the approved workflow continue. ClickHouse's query must cause that target choice; its measured diverse replay workload addresses the sponsor's scale/latency rubric separately. Guild's hosted work and permission boundary must be actual. A template may replace the investigator reasoning in some production designs; do not claim the model is logically necessary.

**Concession:** this is a credible two-sponsor demonstrator, not a defensible new security category. Pi innovation appeal may remain limited.
