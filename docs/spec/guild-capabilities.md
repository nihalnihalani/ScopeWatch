# ScopeWatch: Guild capability audit and minimum credible flow

Research-only expansion, 9 October 2026. No account test, hosted execution, policy change, measured latency or project build was performed. Event scope remains one project, at most four people, 11:30 AM–4:30 PM PT; Akash is excluded. This audit reuses six primary captures and adds six canonical primary pages, with a full OpenAPI variant for the task endpoint. Raw captures and the source/section indexes are under `.firecrawl/docs.guild.ai/` and `.firecrawl/scopewatch-kb/guild/`.

**Guild can make ScopeWatch a real permission-use investigation and selective subsequent-call containment demonstration. Its minimum evidence supports a declared access-capacity violation, not proof of data theft, intent, successful reads or a prompt-injection exploit.** The stronger story is an operator-approved support workload exceeding its own credential-operation allowance across real sessions while an explicitly approved bulk workload using the same credential remains permitted and useful. The model explains the trusted purpose and assembles a reviewable case; SQL establishes the violation; Guild enforces the precise reviewed rule.

## 2. Native event, identity and clock contract

The collector should retain raw source rows, rather than manufacture a flat `agent_id` and call it native evidence. The public schema describes optional/unconstrained projections; actual population remains a first-hour gate.

| Source field or join | Established meaning | Minimum handling |
|---|---|---|
| Security event `id` | Unique native UUID; event endpoint says UUIDv7 IDs are time-ordered. | Deduplicate native events with session identity retained. Use only durable IDs as cursors; streamed/reasoning draft IDs are ephemeral and rejected. |
| `created_at`, `updated_at` | Native date-time fields; API-trigger examples define event creation as when recorded and update as when last updated. | Choose and display **Guild event record-creation time** for the window after confirming returned values. Do not call it exact service-delivery time. Never substitute `updated_at` or collector arrival silently. |
| `decision` | ALLOW, DENY or ERROR. | Count ALLOW only for the chosen operation family. Display DENY/ERROR separately; ERROR is not a successful refusal or delivery. |
| `operation`, `reason_code` | Operation evaluated; stable reasons include `ACCESS_ALLOWED`, `POLICY_DENIED`, `CREDENTIAL_UNAVAILABLE`, `PRIVILEGE_ESCALATION_DENIED`, `PLATFORM_ACCESS_DENIED`. | Count the selected exact operation. Distinguish a policy denial from missing credentials or platform access denial. Additional reason codes are documented investigation signals, not tested attack detectors. |
| `credentials_id`, `capability`, `details` | Credential UUID, capability such as read/write/delete/admin, and structured audit context; these are nullable/optional. | Credential identity must be populated and authenticated for the shared-credential claim. No guaranteed native top-level repository, URL, recipient, object IDs or request path is promised. Missing fields produce evidence warnings. |
| Security `task_id` → native task graph | The event references a task; task endpoint provides `id`, `session_id`, `parent_task_id`. | Resolve to the actual agent task, following native parent links where necessary. Test whether security references the agent task or a tool task. Keep raw mapping and reject ambiguous joins. |
| Agent task identity | `TaskAgent` has `version_id`, `agent` and `version` projections; schema leaves `agent` as `{}`. API-trigger examples show `agent.id` in agent tasks. | Cross-check the returned authenticated agent/version against the controller's recorded launch of the installed agent. Never use an agent/tool payload's self-declared ID. Avoid sub-agents in the minimum so attribution stays simple. |
| Session identity | Returned `id`, `session_url`, workspace, trigger and root task. | Preserve the returned session/root-task/workspace IDs and launch record. Session ID identifies a run, not a workload by itself. Group by the verified agent + workspace + credential + selected operation, under a versioned manifest. |
| Tool task outcomes | `tool_call_id`, `tool_name`, status, nullable `http_status_code`, `request_bytes`, `response_bytes`; `response_data` exists only when the response was projected due to size. | Optional outcome correlation. Agent task DONE does not guarantee every tool succeeded. A 2xx records HTTP response status, not meaningful content delivery. Missing `response_data` is expected and cannot be repaired by inventing receipts. |

[Event schema](https://docs.guild.ai/api-reference/sessions/fetch-session-events), [task schema](https://docs.guild.ai/api-reference/sessions/fetch-session-sub-tasks), [session/identity examples](https://docs.guild.ai/platform/api-triggers).

**Round-2 precision:** task-parent traversal establishes workload attribution only. If a security event references an agent task with multiple tool descendants, do not attach all descendant outcomes to that event. Optional result enrichment needs a demonstrated exact native one-to-one call relation; name/time/sequence matching or a single candidate does not suffice. Keep unmatched and ambiguous outcomes separate. The native-outcome experiment is allowed only after the complete fixed approval-event core works by 1:30 PM, capped at 15 minutes to 1:45; it does not add a receipt service or bridge. See [the focused rebuttal](rebuttal-guild.md).

Use a declared half-open interval, for example `[window_start, window_end)`, and show the clock label with the budget. Record collector observation time separately. UUID ordering supports pagination; decoding its embedded time is unnecessary and does not establish service-execution time. Task `created_at`/`updated_at` and `notified_at` likewise are not authenticated object-served timestamps.

The specific events API defaults to **newest-first, 20 items**, with `limit` capped at 1,000, and `from_id` exclusive (`id > cursor`). Read requires `workspaces:read` **and** `agents:read`; missing the latter currently causes a documented 500. A collector must establish an ascending durable traversal (test `sort_by=id`) or exhaust a stable completed-session snapshot before advancing its high-water mark. Taking the newest returned ID and ignoring `has_more` loses history. General session docs say to take the last ID while paginating; reconcile that guidance with the specific newest-first endpoint in the account test. Re-read/reconcile completed sessions if late persistence can publish lower IDs. A failed/incomplete page is an evidence gap, never zero permission use.

## 3. Smallest readable flow and policy candidate

**Operator's approved workload manifest:** immutable to all three agents; version/hash; verified workspace/agent identity; shared credential identity; selected operation `issues_get`; owned synthetic repository; rolling interval; allowed-decision allowance; purpose and approval reference. Choose low fixture counts for the support workload and a deliberately higher approved allowance for the bulk workload. Fixture counts are planned lab parameters, not measurements or production recommendations.

1. Publish two separately identifiable, deterministic hosted workloads, with only `github_issues_get` for the synthetic fixture tickets. Run several short support-agent sessions and a real bulk-control session. Each counted approval is evidence that the permission gate allowed the selected request; do not label it a returned ticket.
2. Controller records the returned session/workspace/root task and installed-agent launch identity. Collector exhausts native event/task pages, preserves raw rows, checks the identity graph and deduplicates. Missing mapping is visible.
3. ClickHouse groups unique verified ALLOWs across sessions by agent/workspace/credential/operation and applies the operator-owned allowance. The aggregate chooses the case actor and contributing sessions. It does not infer intent or grant itself permission to contain.
4. Start one real Native Guild investigator with the actual bounded aggregate, manifest reference/hash, native session/event IDs, contributing-session summary, proposed scope and evidence limitations. Expose exactly the documented GitHub tools needed to read the manifest (`github_repos_get_content`) and create the incident (`github_issues_create`). Resolve and pin the integration version/tool manifest from the installed integration rather than guessing YAML names or versions.
5. Investigator reads the actual approved purpose/exception context and creates a real incident issue naming count/unit/window, allowance, actor, credential, contributing sessions, missing fields, why the bulk control is approved, and the precise reviewable policy candidate. The case separates facts from interpretation. It cannot change the manifest, evidence, policy or credentials. Its narrative cannot change the deterministic predicate.
6. Operator reviews and applies the selected DENY through Guild's policy UI or documented CLI. Record the policy ID, scope, actor and application observation time. The investigator has no policy-edit authority.
7. Start a fresh selected call by the contained agent and a fresh real selected call by the approved control. Require native target `DENY` with reason `POLICY_DENIED`, plus the control's actual expected synthetic result. If the selected operation returns a known ticket, inspect its real result/HTTP outcome; do not use a model's claim that it succeeded. Preserve both receipts and session links.

A planned policy candidate, **not an executed command**, is:

```bash
guild credentials policy create <verified-shared-credential-id> \
  --decision DENY \
  --operations "issues_get" \
  --resources '{"repos": ["<owned-owner>/<synthetic-repo>"], "methods": ["GET"]}' \
  --agents <verified-target-agent-id> \
  --workspaces <verified-workspace-id>
```

The operation uses the unprefixed policy name; the model/SDK tool has the `github_` prefix. `agents` and `workspaces` are explicit identity dimensions. Policy resource extraction is documented, but the first-hour test must prove the request matches this repo/method scope. Do not claim repo-level analytics merely because the enforcement rule supports repo scope; the event's repo field is optional/unestablished. Removing the default allow-all and narrowly allowing required operations is necessary before claiming a restricted baseline. A matching targeted DENY can override allow-all, but retaining it leaves every unmatched request allowed. [Policy semantics](https://docs.guild.ai/platform/credential-policies), [GitHub tool mapping](https://docs.guild.ai/integrations/github).

## 4. Threat story and untrusted evidence

The minimum misuse is **an agent using a permitted operation more often than its owner approved across sessions**. It is operationally meaningful when the permission is a shared access path to sensitive work, but this synthetic demonstration establishes only the declared capacity violation. The operator's trusted manifest supplies the purpose and allowed capacity; Guild supplies evaluated operation/credential/task evidence; ClickHouse supplies the cumulative fact. The investigator supplies contextual explanation and a useful incident artifact. Platform policy supplies the subsequent refusal.

An optional injected instruction inside a synthetic ticket can tell the support agent to enumerate additional tickets or tell the investigator to raise its allowance. It is external tool data, never authority. In the deterministic lab the violating behavior is explicitly scripted; displaying that text does **not** prove a model was exploited. If an actual model follows it in a measured run, record exact input, tool sequence and outcome as a separate stretch result. Likewise, a forged `agent_id` inside ticket content must never change collector attribution.

External ticket bodies, comments, manifest lookalikes and returned labels are untrusted. The investigator must treat them as cited source content, disregard embedded instructions to change limits or containment, and read the operator-selected versioned manifest reference. The controller validates the incident's proposed actor/credential/operation against deterministic case facts before presenting approval. Restricting the investigator to read/create makes an instruction-bearing response unable to edit the trusted files or policy; still verify that `issues_create` cannot accidentally be used on an unintended repository through broad default policy. Do not grant generic `guildTools`, policy admin, issue-update, credential connection or repository write tools to this investigator.

Resource-purpose drift, recipient-boundary violation, exact returned-object counts, successful data drain, identity escalation and prompt-injection detection are **not** minimum capabilities. They need actual request/outcome fields and trusted declarations/correlation. Native `PRIVILEGE_ESCALATION_DENIED` is a documented reason code, not proof of an attempted exploit in this lab. Native task outcome fields may enrich evidence without a new remote service, but the specific event-to-tool-task match must be proven first.

| 11:50–12:05 | Apply reviewed target agent/workspace/repo/method/operation DENY; fresh target refusal and actual control success using the same credential. | Both fail: scope/isolation promise failed. Target succeeds: primary containment not established. |

| 12:15–12:30 | Investigator creates a real issue from manifest + query/session facts; end-to-end timings separately observed. | Text response or drafted issue is incomplete hosted action evidence. Finish the one loop before adding scale or injection experiments. |

The 45-minute core gate at 12:15 remains compatible with `FINAL_IDEA.md`; the last 15 minutes proves the useful investigator artifact. This is a proposed event-time checklist, not research-time runtime work.

If agent-scoped DENY fails, **do not automatically change enforcement mode** and preserve the original claim. Present the tested limitation and deliberately choose a narrower alternate demonstration with the operator:

- **Stop affected running session:** documented **End session** immediately interrupts running tasks, records who/when, and interrupted sessions cannot resume. It preserves another agent's fresh session, but does not prohibit the target agent's future sessions or only one operation. It proves session interruption, not the core credential-operation containment. [Sessions](https://docs.guild.ai/platform/sessions).
- **Pause the target trigger:** documented deactivation prevents subsequent scheduled/event runs; it does not by itself stop all existing sessions or chat/API paths. Prove the chosen launch path stops and control remains useful; disclose remaining routes. [Security stop controls](https://docs.guild.ai/platform/security-architecture).
- **Disable/archive that agent:** documented archiving removes it from all workspaces and stops it running. This is broader actor-wide disablement, with an availability cost to all that agent's work; other agent identities may remain functional. Verify both, and label the scope rather than calling it operation-specific. [Security stop controls](https://docs.guild.ai/platform/security-architecture).
- **Global credential disconnect:** broad refusal including running sessions is documented; with a shared credential it can interrupt legitimate work. Association deletion must not be presumed effective selective revocation, especially for account-wide credentials and agent-created credentials. Only use this as an explicitly broader emergency-control demonstration, showing its control-workload cost. The reused audit in `debate/02_runtime_advocate.md` covers association semantics.
- **Monitoring/review only:** a real query and incident issue remain useful, but label containment uncompleted. A local boolean, a recommendation or a disabled button does not become Guild enforcement.

## 6. Essential, stretch, cut and adversarial questions

**Essential:** two real agent identities sharing one verified credential; one exact operation and owned repo; trusted versioned per-workload capacity/purpose declaration; complete native event/task mapping and deduplication; clock/persistence caveat; real ClickHouse case selection; one hosted investigator source read and actual incident write; reviewed real scoped policy; target refusal and fresh actual control success.

**Stretch after the complete loop:** native matched HTTP outcomes/response sizes; optional resource context if actually returned; native UI task timing view; BYOK model allowlist/cost controls if already accessible; a measured real prompt-injection run; additional denial-reason triage; administrative policy-action audit receipt if export/access is available. The audit architecture advertises administrative records, but this pass did not verify export API or account access.

**Cut:** general egress service, custom receipt server solely to claim documents, new ClickHouse/Guild integration, multi-agent investigator swarm, automatic LLM policy mutation, provider migration just to show model policy, container agents for the investigator, in-turn prevention claims, recipient/exfiltration detection without evidence, dated “new Guild” claims without release sources.

Three questions the build must withstand:

1. **“Is this only a quota alarm?”** The deterministic predicate is a declared permission-use budget violation. Value comes from authenticated cross-session attribution, approved-purpose/exception context, a real hosted investigation, the precise credential-operation action, and proof that useful work on the same credential continues. If those are missing, the objection is correct.
2. **“Did those ALLOWs mean the agent obtained anything, or did it retry failures?”** No. Minimum counters are permission decisions. Show any matched native tool HTTP outcome separately, disclose retries/missing outcomes, and avoid object/bytes-leaked labels. Use the actual synthetic result only for the fresh control-success witness.
3. **“How do you know you blocked this workload rather than the shared credential, a session, or a tool hidden in its prompt?”** Preserve the authenticated task/agent/version/credential mapping, exact applied rule, fresh `POLICY_DENIED` target event and fresh control result using the same credential. If agent/workspace/resource match or continued success is absent, selective operation containment is unproved.
